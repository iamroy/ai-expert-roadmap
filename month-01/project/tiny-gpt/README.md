# Month 01 Project — Build a Small GPT-like Transformer

**Depth: MASTER**

**Goal:** implement and inspect a complete next-token language model in plain PyTorch, then defend its behavior with tests and experiments.

[Month 1 roadmap](../../README.md) · [Exit test](../../exit-test.md) · [Progress notes](../../progress.md)

This is a learning-scale model, not a production chatbot. It should make every stage of the computation visible. Start with a byte or character tokenizer, learned positions, explicit causal multi-head attention, a pre-norm block, and a GELU FFN. After the baseline works, compare one modern substitution at a time.

## Data flow

```text
raw text → tokenizer → fixed-length windows → shifted inputs / targets
                                │
                                ▼
                  token embeddings + positions
                                │
                     ┌──────────▼──────────┐
                     │ LayerNorm           │
                     │ Q/K/V projections   │
                     │ causal attention    │
                     │ output + residual   │
                     │ LayerNorm → FFN     │
                     │ output + residual   │
                     └──────────┬──────────┘
                         repeat L blocks
                                │
                         final LayerNorm
                                │
                          vocabulary head
                                │
                       logits [B, T, V]
                       /              \
     shifted targets → loss       final position
                         │             │
                 backward / AdamW   sampler → append token → repeat
```

## Environment

Use Python 3.12 and PyTorch 2.14 for the verified reference environment. A CPU is sufficient for the small default configuration; no API keys, model download, or private dataset are needed. Create an isolated environment from this project directory:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install torch==2.14.0
```

Use a PyTorch version compatible with your platform if that wheel is unavailable, and record the version used. The code avoids a high-level trainer and pretrained model wrappers so the data and gradients remain visible.

## Milestone 1 — Data contract and tokenizer

Create a tiny synthetic corpus or use text whose license permits the intended use. Record its source, license/provenance, and preprocessing. Define the vocabulary and unknown-input policy. Split independent documents before sampling windows so overlapping text does not leak across splits.

Implement an encoder and decoder and test ordinary text, Unicode, whitespace, and empty input. For a byte vocabulary, distinguish valid input round trips from decoding arbitrary generated bytes. Document whether BOS/EOS exist and how generation stops.

**Deliverable:** a data manifest and two disjoint source-document lists. A synthetic dataset that reuses templates is suitable for mechanics, but its held-out score measures a narrow kind of generalization.

## Milestone 2 — Shifted training batches

Implement a batch sampler returning two integer tensors of shape `[B,T]`. Ensure every sampled window has `T+1` stream tokens available. Draw input and target from the same window, shifted by one position. Reject data that is too short.

Print a short batch decoded as text and as IDs before training. Check the final target as carefully as the first. Use fixed-length windows without padding initially; add loss and attention masking only as a separate extension.

**Deliverable:** a deterministic batch fixture and a written explanation of each target position.

## Milestone 3 — Inspectable transformer

Build token and position embeddings, a causal attention module, a pre-norm block, a stack of blocks, final normalization, and a vocabulary projection. Support configurable layer count, width, heads, and context length. Reject invalid head dimensions and overlong inputs.

Make Q, K, V, attention probabilities, and block outputs inspectable without retaining training computation graphs unnecessarily. Use the shape walkthrough in lesson 1.1. Keep attention coefficients available only for requested diagnostic passes; materializing/storing them at production scale is expensive.

**Deliverable:** a forward-pass shape trace and parameter count. Explain which dimensions index tokens, heads, features, and vocabulary entries.

## Milestone 4 — Train and validate

Use AdamW and raw-logit cross-entropy. Record the random seed, configuration, token counts, and loss. Test the forward pass and causality before believing a decreasing loss curve. First overfit a fixed tiny batch as a diagnostic, then use separate train/validation streams.

Validation should use evaluation mode and disabled gradient tracking, restore the previous mode afterward, and aggregate token loss correctly. Save the model configuration with its state and tokenizer description. Verify that reloading reproduces logits in evaluation mode. A model-only checkpoint is sufficient for inference; exact training resumption additionally needs optimizer, RNG, data-order, and step state.

**Deliverable:** initial/final train and validation loss, parameter count, runtime, and a checkpoint reload comparison. Do not represent the small synthetic reference run as a benchmark of general language quality.

## Milestone 5 — Generate and compare

Implement greedy, temperature-only, top-k, and top-p generation. A combined top-k/top-p mode is optional; if included, document the ordering. Reject invalid configurations and return a termination reason. Preserve or explicitly restore training/evaluation mode when generation ends.

Use a bounded context policy. Explain whether it recomputes the last window or uses a KV cache and how positions are handled. For the initial uncached implementation, resetting learned positions when cropping is a documented sliding-prefix baseline, not a proof of equivalence to unlimited context.

**Deliverable:** at least five fixed prompts; three seeds per stochastic mode; output length, repeated-fragment observations, and one failure example per mode. Compare outputs from the same checkpoint and state whether speed measurements include prefill.

**Expect modes to coincide, and be able to say why.** On a small model fitted to a narrow corpus, `temperature` and `top_k` frequently produce byte-identical text at the same seed. That is not a bug in your sampler. It happens because the trained distribution is extremely peaked, so the top-k cut removes only tokens that had almost no chance of being drawn, and the same seed then yields the same draw. Measure it rather than assuming either way:

```python
import torch

model.eval()
ids = torch.tensor([encode("the cat ")], dtype=torch.long)
mass = []
for _ in range(60):
    logits, _ = model(ids[:, -model.cfg.context:])
    distribution = sampling_probs(logits[0, -1], temperature=1.0, top_k=None, top_p=1.0)
    mass.append(distribution.sort(descending=True).values[:20].sum().item())
    ids = torch.cat((ids, distribution.argmax().view(1, 1)), dim=1)

print(f"mean probability mass inside the top 20: {sum(mass) / len(mass):.6f}")
print(f"minimum across 60 steps:                 {min(mass):.6f}")
```

The reference run gives a mean near 0.9992 and a minimum near 0.9952, so `top_k=20` is discarding roughly 0.1% of the mass. Report that measurement alongside the identical outputs; it is the honest finding, and it is the same reasoning lesson 1.6 asks for when it warns against reading random variation as a quality difference. If you want the modes to visibly diverge, raise the temperature, lower `k`, or use a less thoroughly fitted checkpoint — and say which you did.

## Milestone 6 — Required diagnostic tests

Implement tests for these behavioral properties:

- Tokenizer round trips and documented generated-byte decoding behavior.
- Correct shift at the first and last positions of a sampled window.
- Q/K/V and logit shapes; attention rows sum to one before dropout.
- Zero probability on future positions and unchanged earlier logits when only future inputs change.
- Finite loss and nonzero gradients on an ordinary training batch.
- Loss decreases when deliberately overfitting a fixed diagnostic batch.
- Greedy/top-k/top-p behavior, normalization, and invalid sampler settings.
- Deterministic sampling with a fixed seed in the same CPU environment.
- Rejected empty/overlong model inputs and too-short training streams.
- Checkpoint reload equivalence and correct mode restoration after evaluation/generation.

These are test requirements; compare implementation approaches only after making your own attempt.

## Architecture review questions

1. Where do token and position information meet? Which parameters receive gradients?
2. How can training score all positions at once while generation remains sequential?
3. How would RoPE, RMSNorm, SwiGLU, and GQA change this implementation?
4. Which operations would a KV cache avoid, and what additional tests would it require?
5. Why can low loss on the synthetic corpus coexist with poor generated language?

<details>
<summary>Show answers</summary>

1. Learned input embeddings are added to learned position rows. Gradients flow through the head, blocks, projections, normalization parameters, and both embedding tables used in the batch.
2. Training has the true prefix at every position and a mask that prevents leakage. Generation must choose each missing next token before it can form the next prefix.
3. RoPE rotates Q/K rather than adding the current position table; RMSNorm changes normalization statistics; SwiGLU uses a gated three-matrix FFN; GQA reduces distinct K/V heads while preserving query heads. Each requires consistent configuration and new equivalence/shape tests.
4. Cached inference avoids recomputing previous K/V and their prefix states. Verify positions, causal alignment with one query against many keys, cache growth/reset, and equality against an uncached forward pass on the same uncropped prefix.
5. A narrow repetitive corpus is easy to fit and tests little beyond its templates. Byte-level generation can also emit malformed text. Broader language quality needs diverse, independent data and task evaluation.

</details>

## Optional extensions

After the baseline passes its checks, choose one: sinusoidal or rotary positions; RMSNorm/SwiGLU; grouped-query attention; a KV cache; or an optimized attention kernel. Hold data and training budget fixed where practical. Record both correctness and quality/cost changes. Do not implement all extensions at once and lose the ability to attribute a failure.
